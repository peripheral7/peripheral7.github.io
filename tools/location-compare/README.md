# 여기살까? — 입지 비교 (블로그 `/WhereTo/`)

후보지 여러 곳을 **지도**와 **주요 방문지(최대 3곳)까지의 이동 점수**로 비교하는 한 화면짜리 도구.
2026-10-12 처음부터 다시 만들었다(이전 판의 비교 표·상세 화면·후보/거점 관리 화면·DB 흉내는 모두 삭제).

- 주소: <https://peripheral7.github.io/WhereTo/> · 게시판 카드 `content/posts/10-location-compare.json`
- 소스: 이 폴더 → `npm run build` → `public/WhereTo/`(빌드 결과도 git 에 올린다. 배포 워크플로는 복사만 한다)
- 화면 구성·조작 정리: [UI-UX.md](UI-UX.md) · 진행 기록·남은 일: [PROGRESS.md](PROGRESS.md)

## 1. 기능

밝은 테마. 넓은 화면 배치:

```
┌ 교통평점 카드   ┐ ┌──────────────── 지도 ────────────────┐ ┌ 입지 요인 ⚙ ┐
‹ 3D집·후보지    › │ [검색창]  [장단점 기준][후보지 한번에 보기] │ │ 지수 한 줄씩 │
│ 종합·수단 막대  │ │                              + ◎ −   │ │             │
│   1 2 3 4      │ │                                       │ ├ 출퇴근 인사이트┤
├ 주요 목적지     ┤ └───────────────────────────────────────┘ └─────────────┘
┌ 추천 매물 ┐ ┌ 후보지별 비교(지도 폭): 줄 이름 | 카드1 | 카드2 | … ┐ ┌ 카페·식당 ┐
```
1320px 이하: 왼쪽 | 지도, 그 아래 입지 요인·출퇴근 인사이트(나란히) → 후보지별 비교 → 추천 카드 두 장. 900px 이하: 지도 → 수단 점수 → 선택한 후보지 → 카드 → 입지 요인 → 추천 카드 순으로 쌓인다.

| 영역 | 하는 일 |
|---|---|
| 교통평점 카드(왼쪽 위, 10-14) | 고른 후보지 + 점수를 한 카드로: **3D 집 그림**(아이소메트릭 SVG, 지붕 색 = 순위) · 종합 n위·보증금/월세 · 이름·주소 · **주요 교통수단**(주 방문이 가장 많은 목적지에 실제로 가장 크게 반영된 수단 = 가중치 × 점수 최대, 도보권이면 도보 — 시간·노선) · 종합 원형 그래프 · 수단별 **교통평점** 눈금 막대(대중교통·차량·도보, 자전거를 켜면 자전거도 — 그 수단을 점수에 넣은 목적지들을 주 방문 비율로 평균). 카드 가운데 큰 3D 집을 원이 둘러싸고 원 테두리 = 종합 점수 %, 그 아래 점수·순위. **⚙** 에서 라이프스타일 고르기(대중교통 출퇴근 95·5·0 · 자차 출퇴근 5·90·5 · 걸어서 동네 생활 20·0·80 · 자전거 생활 10·0·10·자전거 80 — 대중교통·차량·도보(·자전거) %, `LIFESTYLES`), 창 왼쪽 아래 "세부설정"으로 고른 라이프스타일의 비율을 직접 입력(`pref.lifeCustom`). 카드 안쪽 **왼쪽·오른쪽 가장자리(44px 띠)** 에 마우스를 올리면 어두운 그라데이션 + ‹ › 로 앞·뒤 순위 후보지(끝에서는 반대 끝으로), 카드를 끌어서 넘기기도 된다. 맨 아래 순위 숫자. 카드 높이 = 지도 높이 − 주요 목적지 칸(`contain: size`), 넘치면 카드 안 스크롤 |
| 주요 목적지(왼쪽 아래, 따로) | 목적지마다 이모지·이름·분류·**주 방문 횟수**·이동수단·반영 %. **누르면** 목적지마다 주 방문 횟수(0~14, 0.5 단위)와 **이동수단**(자동 · 🚌 · 🚗 · 🚶 · 🚲) 창. × 로 목적지 빼기 |
| 지도(가운데) | 네이버 지도(키가 있을 때) 또는 밝은 OSM 지도. 번호 원 = 후보지(숫자 = 종합 순위), 이모지 원 = 목적지(분류별 🏫 🏠 🏢 🚉 🛍️ 🏥, 그 밖 📍). **후보지를 고르면 그 후보지와 목적지가 모두 들어오도록 확대·이동**하고 목적지까지 점선. 핀을 누르면 그 후보지 선택. `+` `◎`(다시 맞추기) `−`. 오른쪽 위 "장단점 기준" 옆 **"후보지 한번에 보기"** = 모든 후보지가 고르게 들어오도록 확대·이동(목적지는 빼고). **장단점 글자**: 오른쪽 위 "장단점 기준"(또는 목적지 핀)으로 목적지를 고르면 후보지 옆에 "학교 기준 2위/4"와 장점(＋)·단점(－). 평소엔 고른 후보지에만, 확대 14단계 이상(동네가 구분되는 정도)이면 보이는 모든 후보지에. 문구 규칙은 4-1절 |
| 검색창(지도 위) | 아파트·주소·학교·회사를 한 창에서. **타자를 멈추면(0.45초) 저절로 검색**(Enter 는 바로), 같은 검색어는 다시 안 부름. **띄어쓰기는 너그럽게**: 공백은 하나로 줄여 찾고, 결과가 없을 때만 띄어쓰기를 고친 검색어로 한 번 더(주소 "용인시기흥구덕영대로1732" → "용인시 기흥구 덕영대로 1732", 장소 "망포역래미안" ↔ "망포역 래미안") — `naver.ts` 의 `spaceAddress`·`retryQuery`. 결과는 **지금 지도 가운데에서 가까운 순**(거리 표시)이고 지도에 작은 남색 점. 결과를 누르면 지도가 그 위치로(작은 빨간 점), 결과 목록 오른쪽 바깥에 "후보지로" / "목적지로" → 그 자리에서 등록 창(후보지: 이름·보증금·월세 / 목적지: 이름·분류[학교·본가·직장·기타 + 직접 입력]·주 방문 0~14(비우면 분류 기본값: 학교·직장 주 5 · 본가 주 1 = 월 4 · 그 밖 주 2)). 목적지가 3곳 차 있으면 주 방문이 가장 적은 곳 자리에 들어간다 |
| 입지 요인(오른쪽 위) | 지수마다 같은 모양의 한 줄(이름 · 짧은 설명 · 눈금 · 점수). **쓸 지수는 오른쪽 위 ⚙ 에서 고른다**: 지금 동작하는 것은 🏪 **도보 5분 상권**(기본 켜짐. 이름을 누르면 업종마다 필수/선호/안 봄을 고르는 칸이 열림, 아래 카드 "상권 종합" 줄, 고른 업종의 주요 매장을 지도에 표시 — 4-4절)과 🐈 길고양이 지수(켜면 고른 후보지의 점수 줄 + "사진"·"등록" 링크, 아래 카드에도 한 줄). 🕊️ 평화로움 · 🌳 공원 · 📚 도서관(기본 켜짐, 이름을 누르면 계산 내역 — 4-5절). 쾌적함은 삭제. 설명 문구는 최소로 — 규칙은 "계산 방식" 창과 4-2절에만 |
| 출퇴근 인사이트(입지 요인 아래) | 고른 후보지의 **하루 시간·하루 교통비·월 교통비·월 이동 시간**을 대중교통·차량 나란히. 하루 = 주 방문이 가장 많은 목적지 1회 왕복, 한 달 = 모든 목적지의 (주 방문 × 4) 왕복 합. 아래에 **연비(km/L)·기름값(원/L)** 입력칸(`locCompare.commute.v2` 에 저장). 기름값은 기본이 **자동 = 1순위 후보지가 있는 시군구의 오피넷 평균 휘발유 가격**(입력칸 아래 "오피넷 용인시 평균 · 10/13"), 직접 고치면 "직접 입력 · 자동"(자동을 누르면 되돌림). 공식은 4-3절. 넓은 화면에서 오른쪽 열 높이는 지도(680px)에 맞추고 넘치면 이 칸 안에서 스크롤 |
| 후보지별 비교(아래 가운데, 지도 폭) | 제목 옆 안내 문구 없음. 후보지 카드를 가로로 늘어놓고 CSS subgrid 로 **모든 카드가 같은 줄 높이**를 쓴다. 줄: 후보지(순위·이름·✎ 이름 수정·종합) / 보증금/월세(+ 연한 글씨로 보증금 1,000만원 기준 환산 월세) / 목적지마다 [목적지 점수 · 대중교통(총 분, 대기·정류장까지 도보·환승) · 차량(출퇴근·낮 분, 차이 +분·배율, 네이버 실측 여부) · 도보(분 + "도보권"/"걸어서", 또는 "30분 초과")]. 도보 10분 이내 목적지의 대중교통 칸은 "걸어가니 대중교통 제외". 줄마다 가장 높은 점수는 초록. 카드를 누르면 그 후보지 선택 |
| 추천 카드(비교 양옆, 추후 광고) | 항목마다 **정사각형 사진**(`public/rec/`, 없으면 빈 칸) + 짧은 글. 데이터 `src/recommend.ts`(매물은 "예시" 항목). **왼쪽 추천 매물**: 제목 + 주거용/상가용 꼬리표 · 보증금/월세 · 관리비 · 예상 중개수수료(최대) · 가장 가까운 후보지와 거리(작게) · 특장점 태그. 소개 창에는 한두 줄 설명과 금액표(용도·보증금/월세·관리비·월 부담·예상 중개수수료와 계산식·근거). 누르면 **중개업자 부동산 소개 창**이 페이지 어디서 눌러도 **보이는 화면의 정가운데**에 **지도의 3/4 크기**(화면보다 크면 화면 92%·90% 로)로 열리고 뒤는 20% 어둡게(창이 열려 있어도 뒤 페이지는 스크롤되고 창은 제자리), 창 안은 스크롤되지만 스크롤바는 숨김, 배경 클릭·Esc·× 로 닫힘. body 에 바로 붙인다(portal). **오른쪽 카페·식당**: 이름·종류·주소·가까운 후보지(작게)·특징 키워드, 지도에도 ☕ 핀(갈색 테두리, 확대 14단계부터 이름). 지금은 사용자가 찍은 사진의 실제 카페 4곳(AQUI 영통 신동 · 온커피로스터스 동탄 · 슬로우제이커피공장 용인 처인 · 눜커피 수지 — 후보지 바로 옆은 아님, 주소·좌표는 네이버 지역 검색 2026-10-13). 누르면 네이버지도 검색(`map.naver.com/p/search/검색어`)이 새 탭으로 |
| 계산 방식 | 위쪽 "계산 방식" → 요약 창 |

바꾼 후보지·목적지·선호도는 `localStorage`(`locCompare.v3`)에만 저장된다(이전 판의 선호도 `locCompare.v2` 는 처음 한 번 옮겨 온다).

## 2. 데이터 (`src/data.ts` 기본값 · `src/store.ts` 방문자 저장)

- `CANDIDATES` — 후보지: 이름, 도로명 주소(임시), 위도·경도(손으로 넣은 대략 위치).
- `PROFILES` — **사용자**(위쪽 탭, 10-14 시험용). `me`(나) = `CANDIDATES`·`HUBS`, 그 밖 = 대학교 하나 + 자취 상권 4곳(성균관대 자연과학캠퍼스·아주대·경기대 수원캠퍼스·연세대 신촌). 자취 상권은 상가정보(`data/stores.sqlite`)에서 학교 2km 안을 100m 격자로 훑어 반경 250m 음식점 수가 많은 곳(서로 500m 이상) 중 원룸촌으로 알려진 곳을 고르고, 그 자리 건물의 도로명 주소를 네이버 Geocoding 한 좌표. 사용자마다 저장이 따로(`locCompare.v3` = 나, `locCompare.v3.<id>` = 시험용, 고른 사용자 `locCompare.user`). 시험용 후보지는 검색으로 넣은 후보지와 같은 계산(live.ts)을 쓰되, 자료를 `scripts/bake-profiles.mjs` 로 미리 계산해 `src/profiles-live.json` 에 싣는다(계산 서버가 꺼져 있어도 보임, 같은 값을 `server/cache` 에도 넣어 서버를 켜면 빠진 출퇴근·낮 차량 시간을 기준 시각에 잼). 상권·입지 요인 규칙(`places-config.json` 등)을 바꾸면 `profiles-live.json` 의 `a` 를 지우고 다시 돌린다.
- `HUBS` — 주요 방문지. **`MAX_HUBS = 3`**: 4곳 이상 적어도 앞의 3곳만 계산·표시.
- `DEFAULT_PREFERENCE` — 가중치 대중교통 50 · 차량 30 · 도보 20 · 자전거 20(자전거는 켰을 때만), **주 방문** 학교 5회 · 본가 1회(= 월 4회). `WEEKS_PER_MONTH = 4`(월 4회 = 주 1회, 사용자 지정). 10-14 전의 "월 왕복"(trips) 저장값은 단위가 달라 옮기지 않고 분류별 기본값(`defaultWeekly`)으로 바꾼다. "대중교통 이용" 체크(transitUse)는 목적지 이동수단 🚌(hubMode)로 옮긴다.

## 3. 이동 시간 (`estimateTrip` — 실제 경로가 있으면 그 값, 없으면 직선거리 추정)

| 수단 | 실제 값(있으면) | 없을 때 추정(직선거리 d km) |
|---|---|---|
| 도보 | **OSM 보행 길 거리** ÷ 시속 4.7km — `scripts/fetch-paths.mjs` → `src/paths.json`(기본 후보지), 새 후보지는 계산 서버 `/route` 의 `paths` | `d × 1.25 ÷ 4.7 × 60` |
| 자전거 | **OSM 자전거 길 거리** ÷ 시속 15km(같은 파일) | `d × 1.3 ÷ 15 × 60` |
| 대중교통 | **서울특별시 「대중교통환승경로 조회」**(ws.bus.go.kr `getPathInfoByBusNSub`, 버스+지하철, 경기도 구간도 나옴). 응답 `time` = 문 앞~문 앞 전체 시간으로 보고(1.5km 버스 구간 + 정류장 도보 400m 에 21분이라 탑승만으로는 너무 김), 정류장까지·에서 걷는 시간(OSM 보행 길 거리, 실패하면 직선 × 1.25 — TRANSIT.md)과 첫 대기(추정)를 빼고 남은 것을 탑승·환승으로 표시. 환승 = 구간 수 − 1. 여러 경로 중 전체 시간 최소 | 정류장까지 `round(4 + 0.7d)`(3~18분) + 대기 `5 + min(7, round(d/6))` + 탑승(시속 22km) + 환승(≤3km 0 · ≤12km 1 · 그 이상 2회, 1회 5분) |
| 차량 | **네이버 Directions 5 실측**: 출퇴근 = 평일 **08시·18시** 평균, 낮 = 평일 **10시·13시** 평균(각 ±20분 창에서 잰 표본 `samples.am·pm`). 처음 등록한 길은 그 자리에서 한 번 재서 지금이 혼잡 시간대(평일 07~10시·17~20시)면 출퇴근, 아니면 낮 값으로 **임시 저장**(`provisional`, 카드 "(등록 시각)") — 두 기준 중 하나만 먼저 생긴다. 표본이 하나면 "(1회)" | 낮 `max(5, round(d/31×60 + 3))`, 출퇴근 `max(7, round(낮 × 1.52 + 4))` — 하나만 실측이면 다른 쪽은 그 값에서 같은 비율로 |

- 실측이 없는 값은 카드에 **"(추정)"**, 그 아래에 **"실측 예정: 출퇴근 평일 08시·18시 · 낮 평일 10시·13시"**.
- **API 확인(2026-10-14)**: 서울시 환승경로는 공공데이터포털 키(`DATA_GO_KR_SERVICE_KEY`, 개별 칸 `SEOUL_PATHINFO_SERVICE_KEY`)로 동작. 망포·영통·서천 → 경희대는 경로가 나오지만 **수원 → 분당(본가), 수원 서쪽 → 경희대 등 일부는 세 함수(`ByBusNSub`·`ByBus`·`BySubway`) 모두 "XML Parsing Error"** — 그 구간은 추정. 지하철 단독(`getPathInfoBySubway`)은 짧은 구간에서 "경로가 존재하지 않습니다". 버스 도착·위치(서울·경기)는 실시간 값이라 고정 점수에는 안 쓰고(대기 시간 실측용으로 추후), 경기 정류소 조회도 키만 준비됨.
- **대중교통 자료·지도 경로 그림 = [TRANSIT.md](TRANSIT.md)**(10-14): 고른 경로의 구간(`legs`) — 도보(OSM 보행 길, 정류장까지·에서 시간도 이 거리로), 버스(정류장 좌표·노선, 경기 정류소 경유노선 API 의 `routeTypeCd` 로 종류 색, 선은 경기 버스노선 궤적 — 서울 버스만 OSM 자동차 길 근사), 지하철(역 사이 직선·노선 색).
- **대중교통 길찾기 알고리즘 검토**: 직접 만들려면 GTFS(국가대중교통정보센터 TAGO 노선·정류장·시간표) + RAPTOR(라운드 기반, 환승 수 최소·도착 시각 파레토 — OpenTripPlanner 2·R5 가 쓰는 방식) 또는 CSA(Connection Scan). 오픈소스는 **OpenTripPlanner 2**(Java, GTFS+OSM, 도보·환승 통합 — 서버 메모리 2~4GB)·**R5**(Conveyal, 접근성 분석용)·**MOTIS**. 한국 GTFS 는 공식 배포가 없어(TAGO API 를 모아 변환해야 함) 지금은 서울시 환승경로 API + 실패 구간 추정이 현실적. 경로 수가 늘거나 시간대별 배차가 필요해지면 OTP2 를 계산 서버에 올리는 것이 다음 단계.

## 4. 수단별 점수 (10점 만점, `modeScoresForHub`)

**목적지마다 고정된 기준값**(`HubRef`)에 대한 비율로 매긴다 — 그 기준값이면 10점, 더 나쁘면 비율만큼 깎는다(최대 10). 다른 후보지와 비교하지 않으므로 **후보지를 더하거나 빼도 점수가 바뀌지 않는다**(2026-10-13 전까지는 후보지 중 가장 좋은 값이 기준인 상대 점수였다).

- 기준값은 지금 모든 목적지에 같은 기본값 `DEFAULT_REF` = 대기 5분 · 정류장까지 도보 3분(둘 다 이동 시간 추정의 최솟값) · 환승 0회 · 차량 정체 배율 1.5.
- 나중에 **주 목적지 권역**(대학교 입구·업무지구 등)마다 기준값을 미리 계산해 `src/scoring.ts` 의 `HUB_REF`(목적지 id → 기준값)에 넣는다. 그 권역에서 현실적으로 가장 좋은 대기·도보·환승·정체 배율이 10점이 되게.

### 대중교통 — 대기·도보·환승
```
대기점수 = 10 × 기준대기 ÷ 내대기
도보점수 = 10 × 기준도보 ÷ 내도보            (역·정류장까지 걷는 시간)
환승점수 = 10 × (기준환승+1) ÷ (내환승+1)     (0회도 나눌 수 있게 +1 → 0회 10 · 1회 5 · 2회 3.3)
대중교통 = 대기 40% + 도보 40% + 환승 20%     (TRANSIT_PARTS)
```
탑승 시간은 표시만 하고 점수에는 넣지 않는다(요청: 대기·도보·환승의 차이).

### 차량 — 정체 · 거리 대비 효율 · 대로 진입 (10-14, 4-6절)
```
정체     = 10 × 기준배율(1.5) ÷ (출퇴근 ÷ 낮)                         (최대 10)
효율     = 10 × 기준시간(도로 km) ÷ ((출퇴근 + 낮) ÷ 2)                 (최대 10)
           기준시간(d) = 3분 + 60·d ÷ (20 + 40·(1 − e^(−d/15)))  — 짧은 길 시속 20km → 긴 길 시속 60km 에 가까워짐
대로진입 = 후보지 → 가까운 간선도로 자동차 시간 점수(3분↓ 10 · 5분 6 · 10분 2 · 15분 0, 사이 직선) × 도로 등급(1등급 1.0 · 2등급 0.85 · 3등급 0.7)
차량     = 정체 0.4 + 효율 0.4 + 대로진입 0.2   (CAR_PARTS — 대로 진입 자료가 없으면 앞 둘로 다시 나눔)
```
- 대로 진입은 `scripts/places.mjs` 가 후보지마다 계산(`places.json` 의 `access`, 새 후보지는 계산 서버). 간선도로 = OSM trunk·primary·secondary 중 이름 있는 길(지하차도·터널·IC 제외)을 이름별로 묶고, 가장 가까운 3개 도로의 가장 가까운 점까지 OSRM 자동차 경로(routing.openstreetmap.de, 막힘 없는 시간) × 1.2. 도로 등급은 `places-config.json` 의 `access.roadGrade`: **1등급** 동부대로·덕영대로(여러 시를 잇는 광역 간선) · **2등급** 봉영로·영통로·동수원로·효행로·동탄원천로 · **3등급** 삼성1·2로·동탄지성로·기산교, 표에 없으면 OSM trunk·primary = 1, secondary = 2.
- 결과(10-14): 망포역 신원로 덕영대로 1.6분 10 · 망포역 영통로 덕영대로 3분 9.9 · 영통역 청명남로 덕영대로 2.5분 10 · 경희대 서천동로 영통로 3.4분 7.8.

### 도보·자전거 — 시간만
```
도보: 5분 이하 10점 → 30분 0점 (직선), 30분 초과는 카드에 표시하지 않음 (WALK_LIMIT = 30)
      10분 이하 = "도보권" — 걸어간다고 보고 그 방문지 점수에서 대중교통을 뺀다 (WALK_ZONE = WALK_ONLY = 10, 10-14 사용자 지정: 넘으면 대중교통)
자전거(켰을 때): 10분 이하 10점 → 40분 0점, 40분 초과는 계산 안 함 (BIKE_LIMIT = 40)
```

## 4-1. 지도 장단점 문구 (`hubInsights`)

같은 목적지를 두고 후보지끼리 비교한다. 모든 후보지가 같은 값이면 그 항목은 말하지 않는다.

| 장점(＋) | 조건 |
|---|---|
| 도보권 N분 | 도보 20분 이하(WALK_ZONE). 여러 후보지가 함께 붙을 수 있다 |
| 대중교통 최적 | 대중교통 점수 최고 |
| 차량 이동 최적 | 차량 점수 최고(정체 배율 최저) |
| 환승 없음 | 환승 0회이고 다른 후보지는 환승이 있음 |
| 대기 최소 N분 | 대기 최소(장점이 2개 미만일 때만) |

| 단점(－) | 조건 |
|---|---|
| 도보 30분 초과 | 다른 후보지는 걸어갈 수 있는데 이 후보지는 30분 초과 |
| 대중교통 불리 | 대중교통 점수 최하이고 최고와 1점 이상 차이 |
| 출퇴근 정체 N배 | 차량 점수 최하이고 최고와 1점 이상 차이 |
| 환승 N회 | 환승이 가장 많고 1회 이상 |

장점 최대 3개, 단점 최대 2개. 머리에 "목적지 기준 순위/후보지 수"(목적지 점수 순). 둘 다 없으면 머리만 보인다(따로 문구 없음).

## 4-2. 길고양이 지수 (선택 요인, `src/cats.ts`)

입지 요인 중 하나로, 화면 오른쪽 "입지 요인" 카드의 ⚙ 에서 골라 켠다(후보지별 비교 카드에는 넣지 않는다). **종합 점수·순위에는 섞지 않는 별도 지수**다.

- 세는 것: 후보지에서 반경 300m(`CAT_RADIUS_M`) 안의 고양이 수 n — 유효한 사진이 한 장 이상인 고양이만. 참여자 수 u — 그 고양이들에 유효한 사진을 올린 서로 다른 사용자.
- 점수(`catScore`): n=0 → 0 · n=1 → **4** · n=2 → 5.3 · n=3 → 6.7 · n=4 → **8**(한 마리당 4/3점). n≥4 이면 `8 + 0.5 × (u − 1)`, 최대 **10**(참여자 5명 이상).
- 사진 유효 기간 60일(`PHOTO_VALID_DAYS`). 만료된 사진은 셈에서 빠지고(앱을 열 때 저장소에서도 치운다), 사진이 모두 만료된 고양이도 빠진다.
- 한 사람(브라우저마다 만든 임의 ID) 이 고양이 한 마리에 사진 한 장(`addPhotoToCat` 이 거부).
- 현장에서만: 등록 위치 = 내 현재 위치(GPS, 정확도 80m 이내만), 지도에서 찍어 넣는 길 없음, 사진은 `capture="environment"` 로 카메라 호출. 기존 고양이에 사진을 더하려면 100m 안(`FIELD_RADIUS_M`). 입력: 이름(선택)·출몰 시간대(새벽·아침·낮·저녁·밤)·특징. 공원 진출입로 촬영 앱(field_app)의 현장 입력 방식을 참고했다.
- 사진 줄이기(`shrinkPhoto`): 긴 변이 1280px 를 넘으면 줄여 JPEG 품질 0.82 로 저장(EXIF 회전은 반영, GPS 정보는 제거).
- **서버 업로드 꺼짐**(`UPLOAD_ENABLED = false`): 서버가 없어서 등록 내용은 localStorage(`locCompare.cats.v1`)에만 있다. 서버가 생기면 여기서 올리고 다른 사용자와 합친다(참여자 수가 의미를 갖는다). 용량은 localStorage 5MB 안쪽(사진 한 장 약 100~300KB)이라 서버 전에는 수십 장이 한계.

  | 잡화점 | 1 | 2 | 3 | 5 | 1 | 68% | 자료 부족(다이소 거의 미등록) |

  생활권 = 경기·서울에 약 1.1km 간격 격자점을 찍고 반경 500m 안 업소가 100곳 이상인 점(1,093곳, 기준월 2026-06). 기준월이 바뀌면 `analyze` 가 다시 계산해 `COMMERCIAL.md` "생활권 평균 비교"에 적는다(`data/baseline-<기준월>-500.json` 에 저장).
- **카페 가정**: 카페 하나가 "내 마음에 드는 카페"일 확률을 p 라 하면, n곳 중 하나라도 있을 확률은 1 − (1 − p)^n 이다. 아래 업종 점수 식이 바로 이 꼴이고, 기준 50곳에서 9점(90%)이 되는 p 는 약 4.5%(22곳 중 1곳). 많을수록 계속 오르지만 오르는 폭은 줄어든다.
- **잡화** = 개수 점수(기준 6) × 50% + **올리브영·다이소** 매장 점수(기준 1곳) × 50%. 매장은 상호가 "올리브영"·"다이소"로 시작하는 곳(씨제이 등 앞말은 뗌), 80m 안 같은 브랜드는 한 곳. 다이소는 상가정보에 거의 없어 사실상 올리브영.
- 업종 점수 = `10 × (1 − 10^(−개수 ÷ 기준))` — **한계효용 체감**. 처음 몇 곳이 점수를 크게 올리고 기준에서 9점, 기준의 2배에서 9.9점, 그 위로는 아무리 많아도 10점을 넘지 않는다. 기준의 절반이면 6.8점, 0곳이면 0점. 다른 후보지와 상관없는 **절대 점수**(후보지를 더하거나 빼도 안 바뀜).

  | 개수 ÷ 기준 | 0.25 | 0.5 | 1 | 1.5 | 2 | 3 |
  |---|---:|---:|---:|---:|---:|---:|
  | 점수 | 4.4 | 6.8 | 9.0 | 9.7 | 9.9 | 10.0 |
- 상권 지수 = `필수 업종 점수 평균 × 0.8 + 선호 업종 점수 평균 × 0.2`. 묶음 안의 업종은 똑같은 무게. 필수만 고르면 필수 100%, 선호만 고르면 선호 100%.
- (정리 전) 계산 예(옛 기본값, 망포역 영통로): 필수 = 마트 11/10 → 9.2 · 의료 21/30 → 8.0 → 평균 8.6. 선호 = 카페 31/50 → 7.6 · 음식점 138/80 → 9.8 · 화장품(2/5 → 6.0) × 0.5 + (올리브영 0 → 0) × 0.5 = 3.0 → 평균 6.8. 지수 = 8.6 × 0.8 + 6.8 × 0.2 ≈ **8.2**. (기본값 결과: 영통역 청명남로 9.7 · 망포역 신원로 9.2 · 망포역 영통로 8.2 · 경희대 서천동로 4.8)
- 업종 정의(분석 스크립트): 마트 = 슈퍼마켓·대형마트(편의점 제외 — 기준 3이면 어디나 넘침, 아이스크림 할인점·과자점 제외, 입점 매장으로 추정한 대형마트 포함). 의료 = 내과/소아과·이비인후과·치과·외과·산부인과·종합/일반병원 + 약국. 화장품 = 관리 업소(에스테틱·태닝·두피·브로우 등) 이름 제외, 브랜드가 아닌 곳은 1층·지하만. 같은 상호·주소·층 중복 등록은 한 곳.
- **주요 매장 지도 표시**: 필수·선호로 고른 업종의 주요 매장(올리브영·다이소·이마트·트레이더스·홈플러스·롯데마트/슈퍼·노브랜드·코스트코·킴스클럽·스타벅스)을 작은 이모지 원으로, 확대 14단계부터 브랜드 이름도. 점선 테두리 = 입점 매장으로 추정한 대형마트. 목록은 후보지 1km 안(`majors`). 상권 지수를 끄면(⚙) 매장 표시도 사라진다.
- 자료는 **기본 후보지(`src/data.ts`)만** 있다. 검색으로 넣은 후보지는 "상권 자료 없음"·"—"(공개 사이트는 API 를 부르지 않는다). 넣고 싶으면 `data.ts` 에 넣고 `node scripts/stores.mjs analyze` 후 빌드.

### 공원(0~10, 더하기 방식 — 감점 없음)
- **공원 = 공간시설 UQ162 의 공원 경계.** 유형은 관리번호(MNUM) 안 시설 코드 UQTxxxx 로 가른다(`places.mjs` 의 `PARK_TYPES`). 경기도 전체에 들어 있는 공원 유형(건수): 어린이공원(UQT21xx) 2,522 · 근린공원(UQT220x) 1,713 · 소공원(UQT26xx) 887 · 문화공원(UQT221x) 277 · 수변공원(UQT251x·29xx) 374 · 체육공원(UQT250x) 187 · 역사공원(UQT222x) 33 · 도시농업공원(UQT23xx) 9 · 묘지공원(UQT24xx) 13 · 유형 미상 공원(UQT20xx) 1,068 · 도시자연공원구역(UQT6000) 10. 같은 자료의 녹지(완충·경관·연결녹지 UQT3xxx)·광장(UQT1xxx)·유원지(UQT4000)·공공공지(UQT5xxx)는 공원으로 세지 않는다(녹지는 녹지 비율에만 넣음). **묘지공원은 제외**(`excludeTypes`). 0.1ha 이상만.
- 이름: 공간시설의 별칭(ALIAS)은 83% 가 비어 있거나 "근린공원1" 같은 번호라서, 그때는 그 경계 안에 드는 OSM 공원 이름을 붙인다(가운데가 안에 들거나 꼭짓점 절반 이상이 안에 드는 것 중 가장 큰 것). 둘 다 없으면 "이름 없는 근린공원" 처럼.
- **공원마다 점수** = `10.6 × log10(공원 안 산책로 길이 ÷ 260m)`, 최소 1점 · 최대 10점. 산책로 = 공원 경계 안을 지나는 OSM 보행로(footway·path·pedestrian·cycleway·track·steps) 길이. 넓이보다 "걸을 거리"가 공원 체감을 잘 갈라서 이것으로 했다. 사용자 예시에 맞춘 값(OSM 경계 기준으로 맞췄고, 공간시설 경계로 바꾸며 조금 달라짐):

  | 공원 | 산책로 | 점수 | 사용자 예시 |
  |---|---:|---:|---:|
  | 소규모 근린·어린이공원 | ~0.3km | 1 | 1 |
  | 반달공원 | 0.40km | 2.0 | 2 |
  | 신동수변공원 | 1.34km | 7.6 | 7~9 |
  | 글빛누리공원 | 1.47km | 8.0 | 7~9 |
  | 광교호수공원 | 31.8km | 10 | 10 |

  서그내근린공원(예시 5점)은 OSM 에 이름이 없어 아직 확인 못 했다.
- **연결성 ×1.8**: 막다른 공원이 아니라 길게 이어져 다른 상권까지 닿으면 — 가장 먼 두 점이 600m 이상, 길쭉함(둘레² ÷ 4π·넓이) 4 이상, 양 끝 각각 150m 안 업소 10곳 이상. (최대 10점)
- **산길 감점(2026-10-13)**: 사용자 — 영통중앙공원은 산길이라 효용이 낮다. 고도 = **Copernicus DEM GLO-30**(유럽우주국, 30m 격자, 무료·키 없음, AWS 공개 데이터 `copernicus-dem-30m`, `data/copdem30-N37E127.tif` 49MB, git 제외 — 받는 명령은 `places.mjs` 맨 위). 공원 안 30m 격자 고도의 상위 10% − 하위 10% = **고저차**. 10m 이하 그대로 → 40m 이상 × 0.4(사이는 직선, `park.slope`). 결과: 평지 공원 1~7m(감점 없음) · 서천근린 12m ×0.96 · 이름 없는 근린 19m ×0.83 · **영통중앙공원 39m ×0.42 (9.8 → 4.1)** · 이름 없는 근린 77m ×0.4. 산책로 평균 경사(오르내림 ÷ 길이)도 재서 `PLACES.md` 에 적지만, DSM(나무·건물 높이 포함)과 30m 격자 잡음 때문에 평지 공원도 6~10% 가 나와 점수에는 안 쓴다. 더 정확히 하려면 국토지리정보원 수치표고모델(DEM 5m, 지면 높이 DTM — 국토정보플랫폼에서 신청·내려받기)로 바꾸면 된다(`loadDem` 하나만 교체).
- **후보지 점수** = **500m 안**(공원 경계까지 거리, 2026-10-13 사용자 지정 — 전에는 1km, 500m 넘으면 줄임) 가장 좋은 공원 점수(500m 안은 거리 감점 없음) + 두 번째 공원의 10% + 500m 원 안 녹지 비율(공간시설 공원·녹지 + OSM 숲·풀밭, 50m 격자로 셈) 15% 이상 +0.5 · 30% 이상 +1, 최대 10.
- 한계: OSM 에 공원 안 산책로가 안 그려진 곳은 둘레의 절반으로 보아 낮게 나온다. 공간시설은 "결정된" 도시계획시설 경계라 아직 조성 안 된 곳도 있을 수 있다(조성 정도는 추후 반영).

## 4-3. 출퇴근 인사이트 (`src/commute.ts`)

점수가 아니라 고른 후보지의 시간·돈을 보여 주는 칸. 이동 시간은 3절 추정(차량은 네이버 실측이 있으면 그 값)을 그대로 쓴다.

| 항목 | 대중교통 | 차량 |
|---|---|---|
| 편도 시간 | 대중교통 전체(도보 10분 이내 목적지면 걸어간 시간) | **출퇴근 시간대** 소요 |
| 편도 비용 | `1,500원 + ⌈(d − 10) ÷ 5⌉ × 100원`(직선거리 d > 10km 일 때, `transitFare`), 도보 10분 이내면 0원 | `도로 km ÷ 연비 × 기름값` — 도로 km 는 네이버 실측 거리(출퇴근 → 여유 순), 없으면 직선 × 1.3(`ROAD_FACTOR`) |
| 왕복 | 편도 × 2 | 편도 × 2 |

- **하루** = 주 방문 횟수가 가장 많은 목적지(주 목적지) 1회 왕복.
- **한 달** = 목적지마다 `주 방문 × 4 × 왕복`의 합(시간·비용 모두). 학교·직장 주 5회 = 월 20회 왕복.
- 연비 기본 12km/L(`DEFAULT_KMPL`).
- **기름값 = 오피넷 평균 휘발유 가격**(`src/fuel.ts`): **1순위 후보지** 주소의 "시도 시군구"(예: 경기도 용인시 → 경기 용인)로 `src/fuel.json` 의 시군구 평균을 찾는다. 후보지가 여러 시군구에 걸쳐 있어도 **1순위 후보지 지역 하나로** 모든 후보지를 계산한다(같은 기름값으로 비교). 시군구가 없으면 시도 평균, 그것도 없으면 1,700원/L(`DEFAULT_FUEL`). 직접 입력하면 그 값이 우선. `fuel.json` 은 `scripts/fetch-fuel.mjs` 가 이 PC 에서 받는다(10절).
- 금액은 10원 단위 반올림.
- 예(기름값 1,700원/L, 망포역 신원로 → 학교 왕복): 대중교통 34분·3,000원 / 차량 30분·6.6km·940원, 한 달(62회) 대중교통 186,800원 / 차량 69,700원.
- 한계: 대중교통 요금은 수도권 거리비례 요금을 직선거리로 흉내 낸 추정이고, 환승 할인·정기권·주차비·톨비는 없다.

## 5. 가중치 → 방문지 점수 → 종합 점수 (`hubScore`, `evaluate`)

1. **방문지 점수** = 수단 점수의 가중 평균. 가중치는 합이 100 이 아니어도(100 을 넘어도) **합에 대한 비율**로 쓴다(모두 0이면 단순 평균). 예: 120·60·20 → 60%·30%·10%. 설정 창 밖 카드에는 이 비율(`weightShares`, 합 100 으로 반올림)만 보인다.
2. **도보 10분 이내 처리**(`WALK_ONLY`): 그 후보지 → 그 방문지는 걸어간다고 보고 **대중교통을 빼고** 차량·도보 가중치만으로 다시 나눈다(`transitSkipped`). 대중교통 점수 자체는 다른 후보지와의 상대 비교에 그대로 쓰인다.
3. **도보 30분 초과 처리**
   - 그 방문지에 30분 안에 걸어갈 수 있는 후보지가 **하나라도 있으면**: 도보를 넣고, 못 걷는 후보지는 **도보 0점**(카드에는 "30분 초과"만 적는다).
     빼 버리면 남은 수단 가중치로 다시 나눠지면서 못 걷는 후보지가 오히려 유리해지는 역전이 생겨서(실제로 후보 3이 7.3 → 9.2로 뛰었다) 이렇게 정했다.
   - **아무도** 못 걸어가는 방문지(예: 본가 15km)는 도보를 빼고 대중교통·차량 가중치로만 나눈다.
4. **목적지 이동수단**(10-14, `hubMode`): 자동이 아니면 그 목적지 점수 = 그 수단 점수(다른 수단은 카드에 회색 참고). 자동이면 위 1~3. 자전거는 켰을 때만 수단에 들어간다(`activeModes`).
5. **종합 점수** = 방문지 점수를 **주 방문 횟수 비율**로 가중 평균(카드의 "반영 %"). 횟수가 모두 0이면 방문지를 똑같이 본다.
6. **순위** = 종합 점수 순.

### 계산 예 (기본값, 후보 1 → 경희대 국제캠퍼스 1.29km)
- 대중교통: 대기 5분(최소 5 → 10점), 도보 5분(최소 4 → 8점), 환승 0회(10점) → `0.4×10 + 0.4×8 + 0.2×10 = 9.2`
- 차량: 13분/6분 → 배율 2.17, 최저 배율 2.00(후보 3) → `10 × 2.00 ÷ 2.17 = 9.2`
- 도보: 17분 → `10 × (30−17) ÷ 25 = 5.2`
- 방문지 점수: `0.5×9.2 + 0.3×9.2 + 0.2×5.2 = 8.4`
- 종합: 학교 60회(97%) · 본가 2회(3%) → `8.4×0.968 + 10.0×0.032 ≈ 8.5`

(위 계산 예는 좌표를 바로잡기 전·상대 점수 시절 값이다.) 지금 기본값 결과(10-13, 목적지 고정 기준 DEFAULT_REF): 경희대 서천동로 9.4 · 영통역 청명남로 8.2 · 망포역 영통로 7.9 · 망포역 신원로 6.4 (순위는 상대 점수 때와 같음).

## 6. 성질과 한계

- **교통 점수는 목적지 고정 기준**(4절): 후보지를 더하거나 빼도 다른 후보지 점수는 그대로다. 단 지도 장단점 문구(4-1절)는 후보지끼리 비교한 것이라 후보지에 따라 바뀐다. 기준값이 모든 목적지에 같은 기본값이라, 권역별 기준을 넣기 전까지는 "그 목적지에서 현실적으로 가능한 최선" 대비가 아니라 이동 추정의 최솟값 대비다.
- 후보지가 거의 같은 거리면 대중교통 항목이 모두 같아 차이가 안 난다(지금 본가 쪽이 그렇다).
- 짧은 길은 몇 분 차이로도 정체 배율이 크게 흔들린다(6분 → 8분 = 1.33배). 그래서 차량 점수에 거리 대비 효율·대로 진입을 섞었다(4-6절).
- 대중교통 대기 시간은 배차 자료가 없어 추정이다. 서울시 환승경로가 실패하는 구간은 전부 추정.
- 공개 사이트이므로 `data.ts` 의 주소·방문지 이름은 누구나 볼 수 있다(`noindex` 로 검색엔진만 막음).

## 8. 개발 지침

> 새 모듈을 만들 때의 전체 지침(템플릿 구조·필수 확인 사항·**영어판 함께 만들기**)은 [DEV-GUIDE.md](DEV-GUIDE.md). 아래는 요점.

- **영어판(KO/EN)**: 화면 글자는 `t('한국어', 'English')`(`src/i18n.ts`)로 두 언어를 함께 적고, 저장되는 이름·주소·분류는 보일 때만 `pn()`·`addr()`·`catName()` 으로 바꾼다. 계산 방식 창은 한국어판과 `GuideEn` 을 같이 고친다.
- **계산을 바꾸면 세 곳을 함께 고친다**: `src/scoring.ts`(또는 `cats.ts`) → 화면 안 "계산 방식"(`components/GuidePanel.tsx`) → 이 README 3~5절. 화면 배치·조작이 바뀌면 [UI-UX.md](UI-UX.md) 도, 진행 상황은 [PROGRESS.md](PROGRESS.md) 에.
- **숫자 기준은 상수로**: `WALK_LIMIT`(30)·`WALK_ZONE`(10)·`WALK_ONLY`(10)·`BIKE_LIMIT`(40)·`TRANSIT_PARTS`·`CAR_PARTS`·`WEEKS_PER_MONTH`(4)·`BASE_DEPOSIT`·`CAT_*`. 화면 글자와 안내 창은 상수를 가져다 쓰고 숫자를 따로 적지 않는다.
- **화면 문구는 최소로**: 카드·패널에는 값과 짧은 라벨만. 규칙 설명("0점으로 계산", "점수 높은 순 …", 서버 업로드 상태, 점수 구간 등)은 "계산 방식" 창과 README 에만 둔다.
- **가중치는 비율**: 입력은 0~999 정수, 계산은 합에 대한 비율, 설정 창 밖 표시는 `weightShares()`(합 100). 합이 100 이어야 한다고 막지 않는다.
- **배치**: 넓은 화면은 3열 그리드(`.stage`, 줄 `1fr auto auto`) — 아래 줄은 `sideL | cards | right` 라서 후보지별 비교 폭 = 지도 폭. 지도는 최소 680px, 교통평점 카드(`.modes-area`)는 `contain: size` 로 "지도 높이 − 주요 목적지 칸"에 맞춰 줄고 내용은 `.tc-body` 안에서 스크롤(스크롤바 숨김). 후보지별 비교는 **목적지 2곳 기준 높이로 고정**(`CompareCards` 가 왼쪽 줄 이름 칸 높이로 재서 `.cards-scroll` 높이로 — 목적지 1곳이면 첫 목적지 블록 높이로 채움), 3곳이면 세로 스크롤(스크롤바 숨김, 한 스크롤 상자라 모든 카드가 같이 움직이고 후보지 줄은 `sticky`). 왼쪽 광고 칸은 `contain: size` 로 같은 높이(광고가 없어도 자리 유지). 새 영역을 넣을 때는 1320px·900px 미디어 쿼리의 `grid-template-areas` 도 같이 고친다.
- **지도 기능은 두 엔진 모두**: `MapView.tsx` 의 `NaverMap` 과 `OsmMap` 에 같은 동작을 넣는다(예: "후보지 한번에 보기" = `allKey` 를 올리면 둘 다 모든 후보지로 맞춤).
- **추천 카드(광고)**: 항목은 `src/recommend.ts` 의 `LISTINGS`(매물·중개업자 — 용도 `use`·거래 `deal`·보증금·월세·관리비 `maint`·설명 `desc`)·`SPOTS`(카페·식당 — 주소·좌표)만 고친다. 사진은 `tools/location-compare/public/rec/` 에 정사각형 JPEG(sharp `.rotate()` 로 EXIF 회전 반영 후 `fit: cover`, 매물 720px·카페 480px, mozjpeg q80)로 넣고 `recImg(파일명)`. 원본 사진은 저장소 맨 위(git 제외). 가까운 후보지는 좌표로 자동. 실제 업체가 들어오기 전까지 이름에 "예시"를 붙여 진짜처럼 보이지 않게 한다.
- **출퇴근 인사이트**: 요금·연비 기본값은 `commute.ts` 상수. 기름값은 저장값 `fuel: null` = 자동(1순위 후보지 시군구 오피넷 평균, `App.tsx` 의 `fuelAuto`), 숫자면 사용자가 직접 넣은 값. 유가를 새로 받으려면 `node scripts/fetch-fuel.mjs` → 빌드 → 커밋(한 달에 한 번 정도면 충분).
- **창(모달)**: 페이지 위에 뜨는 창은 `createPortal(…, document.body)` 로 붙이고 `position: fixed` + `left/top 50%` + `translate(-50%, -50%)` 로 보이는 화면 정가운데에 둔다. 부모 요소 기준 좌표(getBoundingClientRect 로 위치 계산)로 띄우면 페이지를 내린 상태에서 화면 밖으로 나간다(실제로 있었던 버그). 뒤 페이지 스크롤은 막지 않는다(사용자 요청) — 창 안 스크롤이 뒤로 번지지 않게 `overscroll-behavior: contain`.
- **새 입지 요인**: `Panels.tsx` 의 ⚙ 목록(`SOON`)에서 빼고 켜기/점수 줄을 만든 뒤, 켜짐 상태를 저장(길고양이는 `locCompare.cats.v1` 의 `on`), 카드 줄은 `CompareCards` 의 `rows` 계산에 더한다. 종합 점수에 섞을지는 따로 정한다(지금은 안 섞음).
- **확인**: `npm run typecheck` 후 개발 서버(아래)로 넓은 화면(1600)·1200·휴대폰(375) 폭에서 겹침·가로 스크롤이 없는지 본다. 데스크톱 앱의 미리보기는 저장소 루트 `.claude/launch.json` 의 `location-compare` 설정(5173 포트). 개발 중 `/fonts/` 404 는 정상(배포 사이트 글꼴).
- **배포**: `npm run build` 결과(`public/WhereTo/`)까지 커밋한다. 빌드할 때마다 `assets/index-*.js` 이름이 바뀌니 옛 파일 삭제도 함께 커밋.

## 4-6. 차량 평점 설계 — 거리 보정 · 머신러닝 방안 (10-14)

**문제**: 차량을 시간(또는 거리)으로만 매기면 먼 목적지일수록 점수가 낮아진다 — 후보지 비교에서는 "같은 목적지에 누가 더 빠른가"가 아니라 "거리에 비해 길이 좋은가·막히는가"를 보고 싶다.

**지금 적용한 방식(규칙 기반, 4절)**: 정체 배율(출퇴근 ÷ 낮) + **거리 대비 효율**(그 도로 거리에서 기대되는 시간 ÷ 실제 시간) + 대로 진입. 기대 시간 곡선은 도시 도로의 일반적인 평균 속도(짧은 길 20km/h → 고속·간선 위주 긴 길 60km/h)로 손으로 정했다. 장점: 자료가 적어도 되고 설명 가능. 단점: 곡선이 지역(수원·용인)의 실제 도로망에 맞춰지지 않았다.

**선택지 비교**

| 방식 | 하는 일 | 필요한 자료 | 판단 |
|---|---|---|---|
| A. 손으로 정한 기준(지금) | 거리별 기대 속도 곡선·도로 등급표·진입 시간 표 | 없음 | 바로 쓸 수 있음. 지역마다 조정은 사람이 |
| B. 직접 지정 표본 + 보정 | 사용자가 "이 동네→이 목적지는 몇 점"을 10~20곳 정하면, 그 점수에 맞도록 곡선 계수(20·40·15)·비중(0.4·0.4·0.2)을 최소제곱으로 맞춤 | 사람이 매긴 점수 10~20개 | **추천 다음 단계** — 사용자 감각을 반영, 과적합 위험 작음 |
| C. 머신러닝 회귀 | 네이버 실측(출퇴근·낮 시간·거리)을 특징으로 "거리당 최적 시간"을 학습 → 잔차(실제 − 예측)를 점수로 | 실측 쌍 수백 개 이상(지금 8쌍) | 표본이 쌓인 뒤 |

**머신러닝을 쓴다면(C) 구체안**
1. **자료 모으기**: 계산 서버가 이미 물어본 길마다 08·10·13·18시 표본을 쌓는다(`server/cache/r_*.json`). 여기에 수원·용인·화성·성남의 격자 점(1km) → 주요 목적지(대학·업무지구·역) 쌍을 하루 상한 안에서 매일 조금씩 더해 **2~3달에 1,000쌍 × 4시각** 을 목표.
2. **특징**: 도로 거리, 직선거리, 우회율(도로 ÷ 직선), 출발·도착 대로 진입 시간·도로 등급, 경로 중 간선 비율(OSRM 경로 단계에서), 신호 교차로 수(OSM `highway=traffic_signals`), 시각(08/10/13/18), 요일.
3. **목표**: 실측 시간(분). 모델은 **LightGBM 회귀**(작은 표 자료에 강하고 설명 가능 — SHAP 로 "덕영대로 진입이 2분 단축" 같은 이유를 보일 수 있음). 비교용 기준선은 거리 구간별 중앙값.
4. **점수로 바꾸기**: 그 거리·시각에서 **예측되는 보통 시간 ÷ 실제 시간**(=거리 대비 효율의 학습판), 같은 거리 대역 안 백분위 → 0~10점. 먼 목적지도 "그 거리치고 빠르면" 높은 점수.
5. **검증**: 시간 순 분할(앞 2달 학습 → 마지막 2주 시험), MAE 2분 이하·순위 상관 0.8 이상이면 A 의 곡선을 대체. 모델은 이 PC 에서 학습해 계수·트리를 JSON 으로 내보내고 페이지는 그 결과만 읽는다(공개 사이트에서 학습·API 호출 없음).
6. **주의**: 네이버 Directions 는 "지금 교통"만 주므로 시각별 표본은 그 시각에 재야 한다(사후 수집 불가). 표본이 적은 시각(18시)은 가중치를 낮춘다.

**결론**: 지금은 A 로 계산하고(이미 적용), 사용자가 기준 지역·점수 10~20개를 정해 주면 B 로 계수를 맞춘다. 실측이 수백 쌍 쌓이면 C(LightGBM)로 바꾼다.

## 10. 네이버 API — 키를 숨기고 사용량을 묶는 방법

### 한눈에

| 쓰임 | 네이버 API | 어디서 부르나 | 필요한 키 | 키를 두는 곳 |
|---|---|---|---|---|
| 지도 화면 | 네이버 클라우드 **Maps – Dynamic Map**(JS v3) | 방문자 브라우저 | Client ID 만 | `tools/location-compare/.env.local` 의 `VITE_NAVER_MAP_KEY_ID` → 빌드 때 페이지에 들어감 |
| 주소 검색 | 같은 Maps JS 의 지오코더(`submodules=geocoder`) | 방문자 브라우저 | 위 Client ID 로 함께 | (같음) |
| 장소 검색(아파트·학교 이름) | **NAVER API HUB** 지역 검색(`naverapihub.apigw.ntruss.com/search/v1/local`, 옛 개발자센터 검색 API 는 2026-06-29 종료) | `workers/place-search`(Cloudflare Worker) | Client ID + **Client Secret** | Worker 시크릿(`wrangler secret put`) — git·브라우저에 안 나감 |
| 차량 소요 시간 | 네이버 클라우드 **Maps – Directions 5** | 이 PC(`scripts/fetch-routes.mjs`) | Client ID + Client Secret | `tools/location-compare/.env.local`(git 제외) |

- **지도용 Client ID 는 원래 공개되는 값**이다(페이지 소스에 보임). 네이버 콘솔의 Application 설정에서 **Web 서비스 URL 에 `https://peripheral7.github.io` 와 `http://localhost:5173` 만** 등록하면 다른 사이트에서는 지도가 뜨지 않는다. Secret 은 어떤 경우에도 브라우저 쪽에 넣지 않는다.
- Client ID 는 **필요하다** — 모든 네이버 API 가 Client ID 를 쓰고, 검색·길찾기 REST 는 Client Secret 까지 둘 다 필요하다.
- 콘솔에서는 쓰는 API 만 선택(Dynamic Map·Geocoding·Directions 5)하고 나머지는 켜지 않는다. 키가 새면 콘솔에서 재발급하면 이전 키는 바로 무효.

### GitHub Pages 에 올리면 다른 서버에서 접근할 수 있나 → 있다. 그래서 이렇게 막았다
GitHub Pages 의 파일은 누구나 받을 수 있고, Origin·Referer 검사는 "브라우저만 지키는 약속"이라 서버·스크립트(curl 등)는 헤더를 꾸며 보낼 수 있다. 그래서 출처 검사 하나로는 부족하고, 공개된 검색 중계(`workers/place-search`)에 다음을 겹쳐 걸었다:

1. **하루 전체 상한** `DAILY_LIMIT`(지금 3000 — 실시간 검색에 맞춰 1000에서 올림): 네이버를 실제로 부르기 직전에 D1 에 세고, 넘으면 503 — 무슨 일이 있어도 하루 사용량이 이 선을 못 넘는다(가장 확실한 장치).
2. **IP 당 상한** `IP_HOURLY`(120) · `IP_DAILY`(400): 넘으면 429. IP 는 소금(`SALT`)을 친 해시로만 저장.
3. **Cloudflare Turnstile**(사람 확인): Worker 에 `TURNSTILE_SECRET`, 페이지에 `VITE_TURNSTILE_SITEKEY` 를 넣으면 토큰 없는·틀린 요청은 403 — 브라우저가 아닌 스크립트의 대량 호출을 거른다.
4. **허용 출처만**: Origin 이 블로그·로컬 개발 주소가 아니면 403(다른 웹사이트가 방문자 브라우저로 부르는 것 차단).
5. **7일 캐시**: 같은 검색어는 네이버를 다시 부르지 않고 전체 상한도 쓰지 않는다.
6. **요청 검사**: `GET /search?q=` 만, 2~40자. 화면도 Enter·단추를 누를 때만 검색하고 같은 검색어를 되풀이하지 않는다.
7. 지도 JS·지오코더는 네이버가 Web 서비스 URL 로 인증한다(위 표). 차량 시간은 이 PC 에서만 재고 결과만 올리므로 공개 사이트에는 길찾기 호출이 없다.

로컬에서 가짜 네이버 서버로 확인한 것: 출처 없음·다른 출처 403, 짧은 검색어 400, 첫 검색 MISS → 같은 검색 HIT(네이버 호출 안 늘어남), 전체 상한 초과 503(네이버 호출 정확히 상한만큼), IP 시간당 초과 429, POST 404, Turnstile 실패용 키 403 / 통과용 키 200, 바다 좌표 결과 걸러짐.

### 켜는 순서(키를 받은 뒤)
```bash

# B. 장소 검색: 네이버 클라우드 콘솔 → NAVER API HUB 에서 키 발급(Client ID 10자·Secret 40자, 헤더 X-NCP-APIGW-API-KEY-ID/KEY)

npx wrangler d1 create place-search                 # 나온 database_id 를 wrangler.toml 에
npx wrangler d1 execute place-search --remote --file=schema.sql
npx wrangler secret put NAVER_CLIENT_ID             # API HUB Client ID
npx wrangler secret put NAVER_CLIENT_SECRET         # API HUB Client Secret
#    (보관용 사본: tools/location-compare/.env.local 의 NAVER_HUB_CLIENT_ID / NAVER_HUB_CLIENT_SECRET — Maps 키 NAVER_CLIENT_ID/SECRET 와 다른 키)
npx wrangler secret put SALT                        # 아무 긴 임의 문자열
npx wrangler secret put TURNSTILE_SECRET            # (선택) Cloudflare Turnstile 위젯의 Secret
npx wrangler deploy                                 # → https://place-search.<계정>.workers.dev
#    tools/location-compare/.env.local 에

VITE_TURNSTILE_SITEKEY=Turnstile Site Key           # (선택, TURNSTILE_SECRET 을 넣었다면 필수)

# C. 다시 빌드·커밋
cd tools/location-compare && npm run build
```

### 공공데이터포털 API 키(상권·버스 — 이 PC 에서만)
`tools/location-compare/.env.local`(git 제외)의 `DATA_GO_KR_SERVICE_KEY` 에 넣었다(2026-10-13 상권 storeListInRadius 호출 확인). 값은 data.go.kr 마이페이지의 **일반 인증키(Decoding)**. 한 계정의 키는 승인된 API 모두에 같으므로 보통 `DATA_GO_KR_SERVICE_KEY` 하나만 채우고, 개별 칸은 비워 두면 공용 키를 쓴다. `VITE_` 를 붙이지 않는다(붙이면 공개 페이지에 들어간다). 이름에 숫자를 쓰지 않는다(스크립트의 `.env.local` 읽기가 `[A-Z_]+` 만 받는다).

| 변수 | API | 엔드포인트 |
|---|---|---|
| `SDSC_SERVICE_KEY`, `SDSC_DAILY_LIMIT` | 소상공인시장진흥공단 상가(상권)정보 | `https://apis.data.go.kr/B553077/api/open/sdsc2` (`storeListInRadius`·`storeListInUpjong`·`large/middle/smallUpjongList`) |
| `SEOUL_PATHINFO_SERVICE_KEY` | 서울특별시 대중교통환승경로 조회 | `http://ws.bus.go.kr/api/rest/pathinfo` |
| `SEOUL_BUS_ARRIVAL_SERVICE_KEY` | 서울특별시 버스도착정보조회 | `http://ws.bus.go.kr/api/rest/arrive` |

**작동 방식(한 달에 한 번, 지금은 손으로 실행 — 작업 스케줄러 자동 실행은 보류)**

1. `node scripts/stores-sync.mjs` — 공단에 기준월을 먼저 물어본다(호출 2회). 받아 둔 `data/stores.sqlite` 와 기준월·지역이 같으면 여기서 끝(공단 자료는 분기마다 바뀌어서 대부분의 달은 이 단계에서 끝난다). 다르면 시도별로 1,000건씩 전부 받아 `stores.next.sqlite` 에 쌓고, 지역별 개수가 공단 totalCount 와 맞는지 출력한 뒤 색인(R-tree·FTS)을 만들고 `stores.sqlite` 로 바꿔 끼운다.
2. `node scripts/stores.mjs analyze` — 새 DB 로 후보지 분석을 다시 만든다(`src/commercial.json`·`COMMERCIAL.md`). 후보지나 분류(`commercial-categories.json`)를 바꿨을 때도 이것만 다시.
3. `npm run build` → 결과 파일(`src/commercial.json`·`COMMERCIAL.md`·`public/WhereTo`)만 커밋·푸시. DB 파일은 올리지 않는다(git 제외, 490MB).

**자료의 함정**(`analyze` 결과를 볼 때)
- 대형마트 본점(홈플러스 영통점·트레이더스 수원점·이마트)은 업소로 등록돼 있지 않고 입점 매장만 있다 → 같은 도로명주소에 이름에 브랜드가 든 업소가 3곳 이상이면 거기 있다고 추정(`infer`).
- 다이소는 거의 등록돼 있지 않다(경기·서울 131곳, 영통구 0곳). 잡화점 개수도 믿기 어렵다(생활용품점에 맞는 코드가 없어 주방/가정용품 소매만 셈).
- 올리브영은 대부분(664곳) "그 외 기타 상품 전문 소매업"으로 분류돼 있어 상호로 잡는다. 상호 규칙은 `names_scls` 소분류 안에서만(홈플러스 안 옷가게·카페, 노브랜드 버거가 마트로 잡히지 않게), 주요 매장은 상호가 브랜드로 시작할 때만(TOPTEN키즈홈플러스 같은 오인 방지).

### 관리비 · 용도 · 예상 중개수수료 (`src/brokerage.ts`)

후보지 "수정"과 검색 등록 창에서 **관리비**(월, 만원)를, 수정 창에서 **용도**(주택 · 주거용 오피스텔(전용 85㎡ 이하·부엌·욕실) · 상가·기타)를 넣는다(없으면 주택). 아래 카드 보증금/월세 칸: `보증금 / 월세 · 관리비`, 연한 글씨로 `보증금 1,000 기준 월 ○ · 월 합계(월세 + 관리비)`, `주거용/상가용 · 중개수수료 최대 ○만원`(커서를 올리면 계산식). 추천 매물도 같은 계산.

예상 중개수수료 = 법정 **상한**(실제 보수는 이 안에서 협의, 의뢰인 한쪽 몫, 부가가치세 별도). 근거는 [경기도 부동산 중개보수 요율 안내](https://gris.gg.go.kr/reb/selectRebRateView.do)(2026-10-13 확인):

- **거래금액**: 매매는 매매가. 임대차는 보증금 + 월세 × 100, 그 합이 5천만원 미만이면 보증금 + 월세 × 70(「공인중개사법 시행규칙」 제20조 제5항). 보수 = 거래금액 × 상한요율, 한도액이 있으면 넘지 않음.
- **주택**(「경기도 주택 중개보수 등에 관한 조례」 별표1, 2022.3.4. 시행):

  | 매매·교환 | 상한요율 | 한도액 | 임대차 등 | 상한요율 | 한도액 |
  |---|---:|---:|---|---:|---:|
  | 5천만원 미만 | 0.6% | 25만원 | 5천만원 미만 | 0.5% | 20만원 |
  | 5천만~2억 미만 | 0.5% | 80만원 | 5천만~1억 미만 | 0.4% | 30만원 |
  | 2억~9억 미만 | 0.4% | — | 1억~6억 미만 | 0.3% | — |
  | 9억~12억 미만 | 0.5% | — | 6억~12억 미만 | 0.4% | — |
  | 12억~15억 미만 | 0.6% | — | 12억~15억 미만 | 0.5% | — |
  | 15억 이상 | 0.7% | — | 15억 이상 | 0.6% | — |
- **오피스텔**(시행규칙 제20조 제4항·별표2): 전용 85㎡ 이하 + 전용 부엌·수세식 화장실·목욕시설 → 매매·교환 0.5%, 임대차 0.4%. 그 밖의 오피스텔은 0.9% 이내(→ "상가·기타"로 고른다).
- **그 외(토지·상가 등)**(시행규칙 제20조): 0.9% 이내.
- 건축물 중 주택 면적이 1/2 이상이면 주택, 미만이면 주택 외(제20조 제6항) — 용도를 고를 때 기준. 분양권은 거래 당시까지 불입한 금액(융자 포함) + 프리미엄(아직 계산 안 함).
- 계산 예: 주택 보증금 1,000/월세 50 → 1,000 + 50×100 = 6,000만원 → 5천만~1억 구간 0.4% = 24만원(한도 30만원 안). 보증금 500/월세 30 → 500 + 30×100 = 3,500만원 < 5천만원이라 500 + 30×70 = 2,600만원 → 0.5% = 13만원. 전세 3억 → 0.3% = 90만원. 상가 3,000/150 → 18,000만원 × 0.9% = 162만원.
- 함수: `brokerageFee(용도, 거래, { price | deposit, rent })` → `{ amount, rate, cap, fee(원), vat, basis, formula }`, `dealAmount`, `feeText`. 화면은 지금 임대차만 쓰지만 매매(`deal: 'sale'`, `price`)도 계산된다.

### 보증금 1,000 기준 월세

보증금이 다른 매물을 한 기준으로 비교하려고 `월세 + (보증금 − 1,000) × 연 6% ÷ 12`(만원)로 맞춘다. 보증금 1,000만원 차이 = 월 5만원. 기준 보증금·전환율은 `src/data.ts` 의 `BASE_DEPOSIT`·`CONVERSION_RATE`.

## 11. 새 후보지 계산 서버 (`server/`, 사용자 테스트 기간용)

검색·지도로 넣은 후보지도 상권·평화로움·공원·도서관·차량 시간이 나오게 하는 서버. **이 PC 에서 돌리고 Cloudflare 빠른 터널로 내보낸다** — PC 가 꺼져 있으면 화면에 "계산 서버 꺼짐"(기본 후보지는 그대로 동작).

```
공개 페이지(src/live.ts) → place-search Worker /analyze · /route (허용 출처 · IP 시간당 RELAY_IP_HOURLY)
  → D1 relay 표의 터널 주소(https://….trycloudflare.com, X-Relay-Key = 시크릿 RELAY_SECRET)
  → server/analyze-server.mjs (127.0.0.1:8790, 키가 맞을 때만)
```

- **켜기**: `server/start.cmd` 더블클릭(또는 이 폴더에서 `node server/analyze-server.mjs --tunnel`). 터널 주소는 켤 때마다 바뀌고 Worker 에 자동 등록(10분마다 다시 알림, 25분 소식 없으면 꺼진 것으로 봄). 끌 때 Ctrl+C → 등록 해제. 기록 `server/server.log`.
- **분석(`/analyze`)**: `server/runner.mjs` 가 `server/.work/` 에 저장소 모양 사본을 만들고 `src/data.ts` 만 "후보지 = 이 좌표"로 바꿔 `scripts/stores.mjs analyze` · `scripts/places.mjs --refresh` 를 **그대로** 실행 → 그 후보지 줄만 돌려준다. 스크립트·규칙 파일은 **git HEAD** 에서 꺼낸다(배포 번들과 같은 규칙, 미커밋 변경은 안 섞임). 약 30초, 한 번에 하나(대기열 20), 화면은 4초마다 다시 묻는다. Overpass 주 서버가 바쁘면 사본에서만 미러(z./lz4.overpass-api.de)를 차례로 쓴다.
- **길(`/route`)**: ① 차량 — 네이버 Directions 5(.env.local 의 NAVER_CLIENT_ID/SECRET)는 "지금 교통"만 잰다 → **기준 시각 = 출퇴근 평일 08:00·18:00, 낮 평일 10:00·13:00(각 ±20분 창)**, 두 표본(`samples.am·pm`)의 평균이 그 시간대 값. 처음 묻는 길은 바로 한 번 재서 혼잡 시간대(평일 07~10시·17~20시)면 출퇴근, 아니면 낮 값으로 임시 저장(`provisional`). 물어본 길은 `server/cache/r_*.json` 에 기억 → 10분마다 기준 시각 창 안이면 빠진 표본·30일 지난 표본을 자동으로 잰다(최근 60일 안에 물어본 길만). 기본 후보지도 routes.json 에 두 표본이 다 있지 않으면 같은 방식. ② `paths` — 도보·자전거(OSM 길)·대중교통(서울시 환승경로), `scripts/paths-lib.mjs`, 30일마다 다시. 서버가 답하기 전까지 새 후보지의 대중교통은 "경로 찾는 중"으로 비우고 점수에서 뺀다.
- **대중교통**: 아직 개발 중 — 검색으로 넣은 후보지(`isDefaultCandidate` 가 아닌 곳)는 대중교통 칸을 "개발 중"으로 비우고 점수에서도 뺀다(`scoring.ts` transitPending — 걸어가는 transitSkipped 와 같은 계산).
- **범위·상한**: 서울·경기 네모 밖이면 "서울·경기 밖이라 자료 없음"(공원 경계는 경기만, 고도 보정은 위도 37~38·경도 127~128만). 하루 새 계산 상한 = 분석 150 · 길찾기 300(`.env.local` 의 LIVE_ANALYZE_LIMIT · LIVE_ROUTE_LIMIT, 사용량 `server/.usage.json`). 결과 캐시 `server/cache/`(좌표 30일 · 길·시간대 7일), 브라우저도 `locCompare.live.v1` 에 저장.
- **개인정보**: 서버에는 좌표(소수 5자리)만 오고, 캐시 파일 이름에 좌표가 남는다. 주소·이름은 보내지 않는다.
