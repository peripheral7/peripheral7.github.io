# 여기살까? — 입지 비교 (블로그 `/location-compare/`)

후보지 여러 곳을 **지도**와 **주요 방문지(최대 2곳)까지의 이동 점수**로 비교하는 한 화면짜리 도구.
2026-10-12 처음부터 다시 만들었다(이전 판의 비교 표·상세 화면·후보/거점 관리 화면·DB 흉내는 모두 삭제).

- 주소: <https://peripheral7.github.io/location-compare/> · 게시판 카드 `content/posts/10-location-compare.json`
- 소스: 이 폴더 → `npm run build` → `public/location-compare/`(빌드 결과도 git 에 올린다. 배포 워크플로는 복사만 한다)
- 화면 구성·조작 정리: [UI-UX.md](UI-UX.md) · 진행 기록·남은 일: [PROGRESS.md](PROGRESS.md)

## 1. 기능

밝은 테마. 넓은 화면 배치:

```
┌ 이동수단별 점수 ┐ ┌──────────────── 지도 ────────────────┐ ┌ 입지 요인 ⚙ ┐
│                │ │ [검색창]  [장단점 기준][후보지 한번에 보기] │ │ 지수 한 줄씩 │
├ ‹      ›       ┤ │                              + ◎ −   │ │             │
│ 선택한 후보지   │ │                                       │ ├ 출퇴근 인사이트┤
│   1 2 3 4      │ └───────────────────────────────────────┘ └─────────────┘
┌ 추천 매물 ┐ ┌ 후보지별 비교(지도 폭): 줄 이름 | 카드1 | 카드2 | … ┐ ┌ 카페·식당 ┐
```
1320px 이하: 왼쪽 | 지도, 그 아래 입지 요인·출퇴근 인사이트(나란히) → 후보지별 비교 → 추천 카드 두 장. 900px 이하: 지도 → 수단 점수 → 선택한 후보지 → 카드 → 입지 요인 → 추천 카드 순으로 쌓인다.

| 영역 | 하는 일 |
|---|---|
| 이동수단별 점수(왼쪽) | 고른 후보지의 종합 점수 게이지(0~10 호 위의 점) + 대중교통·차량·도보 **원형 그래프 세 개**(테두리만 점수만큼 수단 색으로 채움, 가운데 점수). 값 = 목적지별 수단 점수를 월 왕복 비율로 평균(도보는 걸어갈 수 있는 목적지만, 대중교통은 도보 10분 이내 목적지 제외). 원 아래에 목적지별 시간(한 줄에 하나, 도보는 30분 안의 목적지만 적고 "30분+" 같은 문구는 없음). 오른쪽 위 "가중치 60·30·10" 은 **합 100 기준 비율**. **카드를 누르면** 그 칸 오른쪽에 수단 가중치 창: 숫자로 입력(0~999, 100 을 넘어도 됨), 합이 100 이 아니면 "100 기준 ○·○·○" 를 보여 줌(계산은 합에 대한 비율) |
| 선택한 후보지(왼쪽 아래) | 제목 없이 박스 맨 위가 **‹ › 단추**(테두리까지 꽉 채운 좌우 반쪽, 순위 순서로 앞·뒤 후보지, 끝에서 처음으로 돎). 이름·주소·순위·보증금/월세, "수정" → 이름·보증금·월세(삭제는 이 창에서만), **주요 목적지 칸을 누르면** 그 칸 오른쪽에 월 왕복 횟수 창, × 로 목적지 빼기. 맨 아래 가운데에 **순위 숫자**(테두리 없음, 고른 것은 진하게). 박스 높이는 지도에 맞추고 넘치면 박스 안에서 세로 스크롤(스크롤바 숨김) |
| 지도(가운데) | 네이버 지도(키가 있을 때) 또는 밝은 OSM 지도. 번호 원 = 후보지(숫자 = 종합 순위), 이모지 원 = 목적지(분류별 🏫 🏠 🏢 🚉 🛍️ 🏥, 그 밖 📍). **후보지를 고르면 그 후보지와 목적지가 모두 들어오도록 확대·이동**하고 목적지까지 점선. 핀을 누르면 그 후보지 선택. `+` `◎`(다시 맞추기) `−`. 오른쪽 위 "장단점 기준" 옆 **"후보지 한번에 보기"** = 모든 후보지가 고르게 들어오도록 확대·이동(목적지는 빼고). **장단점 글자**: 오른쪽 위 "장단점 기준"(또는 목적지 핀)으로 목적지를 고르면 후보지 옆에 "학교 기준 2위/4"와 장점(＋)·단점(－). 평소엔 고른 후보지에만, 확대 14단계 이상(동네가 구분되는 정도)이면 보이는 모든 후보지에. 문구 규칙은 4-1절 |
| 검색창(지도 위) | 하나의 창으로 아파트·주소·학교·회사 검색 → 결과마다 "후보지로" / "목적지로" → 등록 창에서 주요 설정을 정한다(후보지: 이름·보증금·월세 / 목적지: 이름·분류·월 왕복 횟수, 2곳이 차 있으면 바꿀 목적지). **Enter·검색 단추를 누를 때만** 부른다(글자마다 부르지 않음) |
| 입지 요인(오른쪽 위) | 지수마다 같은 모양의 한 줄(이름 · 짧은 설명 · 눈금 · 점수). **쓸 지수는 오른쪽 위 ⚙ 에서 고른다**: 지금 동작하는 것은 🐈 길고양이 지수(켜면 고른 후보지의 점수 줄 + "사진"·"등록" 링크, 아래 카드에도 한 줄). 도보 5분 상권·산책·평화로움·쾌적함은 "준비 중"(⚙ 에서 고를 수 없음). 설명 문구는 최소로 — 규칙은 "계산 방식" 창과 4-2절에만 |
| 출퇴근 인사이트(입지 요인 아래) | 고른 후보지의 **하루 시간·하루 교통비·월 교통비·월 이동 시간**을 대중교통·차량 나란히. 하루 = 월 왕복이 가장 많은 목적지 1회 왕복, 한 달 = 모든 목적지의 월 왕복 합. 아래에 **연비(km/L)·기름값(원/L)** 입력칸(기본 12 · 1,700, `locCompare.commute.v1` 에 저장). 공식은 4-3절. 넓은 화면에서 오른쪽 열 높이는 지도(680px)에 맞추고 넘치면 이 칸 안에서 스크롤 |
| 후보지별 비교(아래 가운데, 지도 폭) | 제목 옆 안내 문구 없음. 후보지 카드를 가로로 늘어놓고 CSS subgrid 로 **모든 카드가 같은 줄 높이**를 쓴다. 줄: 후보지(순위·이름·✎ 이름 수정·종합) / 보증금/월세(+ 연한 글씨로 보증금 1,000만원 기준 환산 월세) / 목적지마다 [목적지 점수 · 대중교통(총 분, 대기·정류장까지 도보·환승) · 차량(출퇴근·낮 분, 차이 +분·배율, 네이버 실측 여부) · 도보(분 + "도보권"/"걸어서", 또는 "30분 초과")]. 도보 10분 이내 목적지의 대중교통 칸은 "걸어가니 대중교통 제외". 줄마다 가장 높은 점수는 초록. 카드를 누르면 그 후보지 선택 |
| 추천 카드(비교 양옆, 추후 광고) | 항목마다 **정사각형 이미지 칸(지금은 비워 둠)** + 짧은 글. 데이터 `src/recommend.ts`(지금은 "예시" 항목만). **왼쪽 추천 매물**: 제목·보증금/월세·가장 가까운 후보지와 거리(작게)·특장점 태그. 누르면 **중개업자 부동산 소개 창**이 지도 가운데에 지도의 절반 크기로 열리고 뒤는 20% 어둡게, 배경 클릭·Esc·× 로 닫힘(900px 이하는 화면 가운데). **오른쪽 근처 카페·식당**: 이름·종류·가까운 후보지(작게)·특징 키워드. 누르면 네이버지도 검색(`map.naver.com/p/search/검색어`)이 새 탭으로 |
| 계산 방식 | 위쪽 "계산 방식" → 요약 창 |

바꾼 후보지·목적지·선호도는 `localStorage`(`locCompare.v3`)에만 저장된다(이전 판의 선호도 `locCompare.v2` 는 처음 한 번 옮겨 온다).

## 2. 데이터 (`src/data.ts` 기본값 · `src/store.ts` 방문자 저장)

- `CANDIDATES` — 후보지: 이름, 도로명 주소(임시), 위도·경도(손으로 넣은 대략 위치).
- `HUBS` — 주요 방문지. **`MAX_HUBS = 2`**: 3곳 이상 적어도 앞의 2곳만 계산·표시.
- `DEFAULT_PREFERENCE` — 가중치 대중교통 50 · 차량 30 · 도보 20, 월 왕복 학교 60회 · 본가 2회(이전 앱에 저장돼 있던 값).

## 3. 이동 시간 추정 (`estimateTrip`, 가상 값)

두 지점의 **직선거리 d(km)** 로 추정한다. 같은 거리면 같은 시간.
단, **차량은 `src/routes.json` 에 네이버 실측값이 있으면 그 값**을 시간대별로 쓴다(여유만 있으면 출퇴근은 실측 여유로 추정). 카드에 "네이버 실측 · 출퇴근 MM-DD HH:MM / 여유 …" 또는 "거리 기반 추정"으로 표시된다. 아래 10절 참고.

| 항목 | 식 |
|---|---|
| 도보 전체 | `max(3, round(d / 4.7 × 60))` (시속 4.7km) |
| 대중교통: 역·정류장까지 도보 | `round(4 + 0.7d)`, 3~18분 |
| 대중교통: 대기 | `5 + min(7, round(d / 6))` |
| 대중교통: 환승 | d ≤ 3km 0회 · ≤ 12km 1회 · 그 이상 2회 |
| 대중교통: 탑승 | `max(4, round(d / 22 × 60))` (평균 시속 22km) |
| 대중교통 전체 | 도보 + 대기 + 탑승 + 환승×5분 |
| 차량 여유 | `max(5, round(d / 31 × 60 + 3))` |
| 차량 출퇴근 | `max(7, round(여유 × 1.52 + 4))` |

실제 API 를 붙일 때는 이 함수만 바꾸면 된다(같은 `Trip` 모양만 돌려주면 점수 쪽은 그대로).

## 4. 수단별 점수 (10점 만점, `modeScoresForHub`)

**같은 방문지 하나를 두고** 후보지끼리 비교한다.

### 대중교통 — 대기·도보·환승의 상대 차이
각 항목에서 가장 좋은(작은) 후보지가 10점, 나머지는 비율로 깎는다.

```
대기점수 = 10 × 최소대기 ÷ 내대기
도보점수 = 10 × 최소도보 ÷ 내도보            (역·정류장까지 걷는 시간)
환승점수 = 10 × (최소환승+1) ÷ (내환승+1)     (0회도 나눌 수 있게 +1)
대중교통 = 대기 40% + 도보 40% + 환승 20%     (TRANSIT_PARTS)
```
탑승 시간은 표시만 하고 점수에는 넣지 않는다(요청: 대기·도보·환승의 차이).

### 차량 — 출퇴근/여유 시간의 상대 차이
```
정체배율 = 출퇴근 ÷ 여유
차량 = 10 × 최저배율 ÷ 내배율
```

### 도보 — 시간만
```
5분 이하 10점 → 30분 0점 (직선), 30분 초과는 카드에 표시하지 않음 (WALK_LIMIT = 30)
20분 이하 = "도보권" (WALK_ZONE = 20, 지도 장점·카드 글자)
10분 이하 = 걸어간다고 보고 그 방문지 점수에서 대중교통을 뺀다 (WALK_ONLY = 10, 5절)
```

## 4-1. 지도 장단점 문구 (`hubInsights`)

같은 목적지를 두고 후보지끼리 비교한다. 모든 후보지가 같은 값이면 그 항목은 말하지 않는다.

| 장점(＋) | 조건 |
|---|---|
| 도보권 N분 | 도보 20분 이하(WALK_ZONE). 여러 후보지가 함께 붙을 수 있다 |
| 대중교통 최적 | 대중교통 점수 최고 |
| 차량 이동 최적 | 차량 점수 최고(정체 배율 최저) |
| 환승 없음 | 환승 0회이고 다른 후보지는 환승이 있음 |
| 대기 최소 N분 | 대기 최소(장점이 2개 미만일 때만) |

| 단점(－) | 조건 |
|---|---|
| 도보 30분 초과 | 다른 후보지는 걸어갈 수 있는데 이 후보지는 30분 초과 |
| 대중교통 불리 | 대중교통 점수 최하이고 최고와 1점 이상 차이 |
| 출퇴근 정체 N배 | 차량 점수 최하이고 최고와 1점 이상 차이 |
| 환승 N회 | 환승이 가장 많고 1회 이상 |

도보 10분 이하(WALK_ONLY)인 후보지는 대중교통 항목(대중교통 최적·환승 없음·대기 최소·대중교통 불리·환승 N회)을 말하지 않는다.
장점 최대 3개, 단점 최대 2개. 머리에 "목적지 기준 순위/후보지 수"(목적지 점수 순). 둘 다 없으면 머리만 보인다(따로 문구 없음).

## 4-2. 길고양이 지수 (선택 요인, `src/cats.ts`)

입지 요인 중 하나로, 화면 오른쪽 "입지 요인" 카드의 ⚙ 에서 골라 켠다(넣으면 아래 후보지 카드에 "🐈 길고양이" 줄이 생긴다). **종합 점수·순위에는 섞지 않는 별도 지수**다.

- 세는 것: 후보지에서 반경 300m(`CAT_RADIUS_M`) 안의 고양이 수 n — 유효한 사진이 한 장 이상인 고양이만. 참여자 수 u — 그 고양이들에 유효한 사진을 올린 서로 다른 사용자.
- 점수(`catScore`): n=0 → 0 · n=1 → **4** · n=2 → 5.3 · n=3 → 6.7 · n=4 → **8**(한 마리당 4/3점). n≥4 이면 `8 + 0.5 × (u − 1)`, 최대 **10**(참여자 5명 이상).
- 사진 유효 기간 60일(`PHOTO_VALID_DAYS`). 만료된 사진은 셈에서 빠지고(앱을 열 때 저장소에서도 치운다), 사진이 모두 만료된 고양이도 빠진다.
- 한 사람(브라우저마다 만든 임의 ID) 이 고양이 한 마리에 사진 한 장(`addPhotoToCat` 이 거부).
- 현장에서만: 등록 위치 = 내 현재 위치(GPS, 정확도 80m 이내만), 지도에서 찍어 넣는 길 없음, 사진은 `capture="environment"` 로 카메라 호출. 기존 고양이에 사진을 더하려면 100m 안(`FIELD_RADIUS_M`). 입력: 이름(선택)·출몰 시간대(새벽·아침·낮·저녁·밤)·특징. 공원 진출입로 촬영 앱(field_app)의 현장 입력 방식을 참고했다.
- 사진 줄이기(`shrinkPhoto`): 긴 변이 1280px 를 넘으면 줄여 JPEG 품질 0.82 로 저장(EXIF 회전은 반영, GPS 정보는 제거).
- **서버 업로드 꺼짐**(`UPLOAD_ENABLED = false`): 서버가 없어서 등록 내용은 localStorage(`locCompare.cats.v1`)에만 있다. 서버가 생기면 여기서 올리고 다른 사용자와 합친다(참여자 수가 의미를 갖는다). 용량은 localStorage 5MB 안쪽(사진 한 장 약 100~300KB)이라 서버 전에는 수십 장이 한계.

## 4-3. 출퇴근 인사이트 (`src/commute.ts`)

점수가 아니라 고른 후보지의 시간·돈을 보여 주는 칸. 이동 시간은 3절 추정(차량은 네이버 실측이 있으면 그 값)을 그대로 쓴다.

| 항목 | 대중교통 | 차량 |
|---|---|---|
| 편도 시간 | 대중교통 전체(도보 10분 이내 목적지면 걸어간 시간) | **출퇴근 시간대** 소요 |
| 편도 비용 | `1,500원 + ⌈(d − 10) ÷ 5⌉ × 100원`(직선거리 d > 10km 일 때, `transitFare`), 도보 10분 이내면 0원 | `도로 km ÷ 연비 × 기름값` — 도로 km 는 네이버 실측 거리(출퇴근 → 여유 순), 없으면 직선 × 1.3(`ROAD_FACTOR`) |
| 왕복 | 편도 × 2 | 편도 × 2 |

- **하루** = 월 왕복 횟수가 가장 많은 목적지(주 목적지) 1회 왕복.
- **한 달** = 목적지마다 `월 왕복 횟수 × 왕복`의 합(시간·비용 모두).
- 연비 기본 12km/L(`DEFAULT_KMPL`), 기름값 기본 1,700원/L(`DEFAULT_FUEL`, 실제 유가 데이터를 붙일 자리). 금액은 10원 단위 반올림.
- 예(기본값, 망포역 신원로 → 학교 왕복): 대중교통 34분·3,000원 / 차량 30분·6.6km·940원, 한 달(62회) 대중교통 186,800원 / 차량 69,700원.
- 한계: 대중교통 요금은 수도권 거리비례 요금을 직선거리로 흉내 낸 추정이고, 환승 할인·정기권·주차비·톨비는 없다.

## 5. 가중치 → 방문지 점수 → 종합 점수 (`hubScore`, `evaluate`)

1. **방문지 점수** = 수단 점수의 가중 평균. 가중치는 합이 100 이 아니어도(100 을 넘어도) **합에 대한 비율**로 쓴다(모두 0이면 단순 평균). 예: 120·60·20 → 60%·30%·10%. 설정 창 밖 카드에는 이 비율(`weightShares`, 합 100 으로 반올림)만 보인다.
2. **도보 10분 이내 처리**(`WALK_ONLY`): 그 후보지 → 그 방문지는 걸어간다고 보고 **대중교통을 빼고** 차량·도보 가중치만으로 다시 나눈다(`transitSkipped`). 대중교통 점수 자체는 다른 후보지와의 상대 비교에 그대로 쓰인다.
3. **도보 30분 초과 처리**
   - 그 방문지에 30분 안에 걸어갈 수 있는 후보지가 **하나라도 있으면**: 도보를 넣고, 못 걷는 후보지는 **도보 0점**(카드에는 "30분 초과"만 적는다).
     빼 버리면 남은 수단 가중치로 다시 나눠지면서 못 걷는 후보지가 오히려 유리해지는 역전이 생겨서(실제로 후보 3이 7.3 → 9.2로 뛰었다) 이렇게 정했다.
   - **아무도** 못 걸어가는 방문지(예: 본가 15km)는 도보를 빼고 대중교통·차량 가중치로만 나눈다.
4. **종합 점수** = 방문지 점수를 **월 왕복 횟수 비율**로 가중 평균(카드의 "반영 %"). 횟수가 모두 0이면 방문지를 똑같이 본다.
5. **순위** = 종합 점수 순.

### 계산 예 (기본값, 후보 1 → 경희대 국제캠퍼스 1.29km)
- 대중교통: 대기 5분(최소 5 → 10점), 도보 5분(최소 4 → 8점), 환승 0회(10점) → `0.4×10 + 0.4×8 + 0.2×10 = 9.2`
- 차량: 13분/6분 → 배율 2.17, 최저 배율 2.00(후보 3) → `10 × 2.00 ÷ 2.17 = 9.2`
- 도보: 17분 → `10 × (30−17) ÷ 25 = 5.2`
- 방문지 점수: `0.5×9.2 + 0.3×9.2 + 0.2×5.2 = 8.4`
- 종합: 학교 60회(97%) · 본가 2회(3%) → `8.4×0.968 + 10.0×0.032 ≈ 8.5`

(위 계산 예는 좌표를 바로잡기 전 값이다.) 지금 기본값 결과(10-13, 도보 10분 규칙 적용): 경희대 서천동로 9.5(학교까지 도보 10분 이내라 대중교통 제외) · 영통역 청명남로 8.7 · 망포역 영통로 8.4 · 망포역 신원로 7.4.

## 6. 성질과 한계

- **상대 점수**: 후보지를 더하거나 빼면 다른 후보지의 대중교통·차량 점수도 바뀐다. 각 항목 1등은 늘 10점.
- 후보지가 거의 같은 거리면 대중교통 항목이 모두 같아 차이가 안 난다(지금 본가 쪽이 그렇다).
- 차량 공식(출퇴근 = 여유×1.52+4분) 때문에 **거리가 짧을수록 정체 배율이 커져** 가까운 후보지의 차량 점수가 낮게 나온다(서천동 → 학교 0.5km 가 8.3). 실제 교통 자료가 들어오면 사라질 성질.
- 이동 시간은 전부 직선거리 추정이다. 실제 노선·배차·도로 사정은 없다.
- 공개 사이트이므로 `data.ts` 의 주소·방문지 이름은 누구나 볼 수 있다(`noindex` 로 검색엔진만 막음).

## 8. 개발 지침

- **계산을 바꾸면 세 곳을 함께 고친다**: `src/scoring.ts`(또는 `cats.ts`) → 화면 안 "계산 방식"(`components/GuidePanel.tsx`) → 이 README 3~5절. 화면 배치·조작이 바뀌면 [UI-UX.md](UI-UX.md) 도, 진행 상황은 [PROGRESS.md](PROGRESS.md) 에.
- **숫자 기준은 상수로**: `WALK_LIMIT`(30)·`WALK_ZONE`(20)·`WALK_ONLY`(10)·`TRANSIT_PARTS`·`BASE_DEPOSIT`·`CAT_*`. 화면 글자와 안내 창은 상수를 가져다 쓰고 숫자를 따로 적지 않는다.
- **화면 문구는 최소로**: 카드·패널에는 값과 짧은 라벨만. 규칙 설명("0점으로 계산", "점수 높은 순 …", 서버 업로드 상태, 점수 구간 등)은 "계산 방식" 창과 README 에만 둔다.
- **가중치는 비율**: 입력은 0~999 정수, 계산은 합에 대한 비율, 설정 창 밖 표시는 `weightShares()`(합 100). 합이 100 이어야 한다고 막지 않는다.
- **배치**: 넓은 화면은 3열 그리드(`.stage`) — 아래 줄은 `sideL | cards | sideR` 라서 후보지별 비교 폭 = 지도 폭. 지도는 최소 680px, 선택한 후보지 칸은 `contain: size` 로 그 높이에 맞춰 줄고 내용은 `.sel-body` 안에서 스크롤(스크롤바 숨김). 새 영역을 넣을 때는 1320px·900px 미디어 쿼리의 `grid-template-areas` 도 같이 고친다.
- **지도 기능은 두 엔진 모두**: `MapView.tsx` 의 `NaverMap` 과 `OsmMap` 에 같은 동작을 넣는다(예: "후보지 한번에 보기" = `allKey` 를 올리면 둘 다 모든 후보지로 맞춤).
- **추천 카드(광고)**: 항목은 `src/recommend.ts` 의 `LISTINGS`(매물·중개업자)·`SPOTS`(카페·식당)만 고친다. 이미지는 `image` 에 주소(정사각형으로 잘라 보임), 없으면 빈 칸. 가까운 후보지는 좌표로 자동. 실제 업체가 들어오기 전까지 이름에 "예시"를 붙여 진짜처럼 보이지 않게 한다.
- **출퇴근 인사이트**: 요금·연비 기본값은 `commute.ts` 상수. 유가 데이터를 붙일 때는 `DEFAULT_FUEL` 대신 받아 온 값을 `loadCommute()` 기본값으로 넣는다(사용자가 고친 값이 있으면 그 값 우선).
- **새 입지 요인**: `Panels.tsx` 의 ⚙ 목록(`SOON`)에서 빼고 켜기/점수 줄을 만든 뒤, 켜짐 상태를 저장(길고양이는 `locCompare.cats.v1` 의 `on`), 카드 줄은 `CompareCards` 의 `rows` 계산에 더한다. 종합 점수에 섞을지는 따로 정한다(지금은 안 섞음).
- **확인**: `npm run typecheck` 후 개발 서버(아래)로 넓은 화면(1600)·1200·휴대폰(375) 폭에서 겹침·가로 스크롤이 없는지 본다. 데스크톱 앱의 미리보기는 저장소 루트 `.claude/launch.json` 의 `location-compare` 설정(5173 포트). 개발 중 `/fonts/` 404 는 정상(배포 사이트 글꼴).
- **배포**: `npm run build` 결과(`public/location-compare/`)까지 커밋한다. 빌드할 때마다 `assets/index-*.js` 이름이 바뀌니 옛 파일 삭제도 함께 커밋.

## 10. 네이버 API — 키를 숨기고 사용량을 묶는 방법

### 한눈에

| 쓰임 | 네이버 API | 어디서 부르나 | 필요한 키 | 키를 두는 곳 |
|---|---|---|---|---|
| 지도 화면 | 네이버 클라우드 **Maps – Dynamic Map**(JS v3) | 방문자 브라우저 | Client ID 만 | `tools/location-compare/.env.local` 의 `VITE_NAVER_MAP_KEY_ID` → 빌드 때 페이지에 들어감 |
| 주소 검색 | 같은 Maps JS 의 지오코더(`submodules=geocoder`) | 방문자 브라우저 | 위 Client ID 로 함께 | (같음) |
| 장소 검색(아파트·학교 이름) | **NAVER API HUB** 지역 검색(`naverapihub.apigw.ntruss.com/search/v1/local`, 옛 개발자센터 검색 API 는 2026-06-29 종료) | `workers/place-search`(Cloudflare Worker) | Client ID + **Client Secret** | Worker 시크릿(`wrangler secret put`) — git·브라우저에 안 나감 |
| 차량 소요 시간 | 네이버 클라우드 **Maps – Directions 5** | 이 PC(`scripts/fetch-routes.mjs`) | Client ID + Client Secret | `tools/location-compare/.env.local`(git 제외) |

- **지도용 Client ID 는 원래 공개되는 값**이다(페이지 소스에 보임). 네이버 콘솔의 Application 설정에서 **Web 서비스 URL 에 `https://peripheral7.github.io` 와 `http://localhost:5173` 만** 등록하면 다른 사이트에서는 지도가 뜨지 않는다. Secret 은 어떤 경우에도 브라우저 쪽에 넣지 않는다.
- Client ID 는 **필요하다** — 모든 네이버 API 가 Client ID 를 쓰고, 검색·길찾기 REST 는 Client Secret 까지 둘 다 필요하다.
- 콘솔에서는 쓰는 API 만 선택(Dynamic Map·Geocoding·Directions 5)하고 나머지는 켜지 않는다. 키가 새면 콘솔에서 재발급하면 이전 키는 바로 무효.

### GitHub Pages 에 올리면 다른 서버에서 접근할 수 있나 → 있다. 그래서 이렇게 막았다
GitHub Pages 의 파일은 누구나 받을 수 있고, Origin·Referer 검사는 "브라우저만 지키는 약속"이라 서버·스크립트(curl 등)는 헤더를 꾸며 보낼 수 있다. 그래서 출처 검사 하나로는 부족하고, 공개된 검색 중계(`workers/place-search`)에 다음을 겹쳐 걸었다:

1. **하루 전체 상한** `DAILY_LIMIT`(기본 1000): 네이버를 실제로 부르기 직전에 D1 에 세고, 넘으면 503 — 무슨 일이 있어도 하루 사용량이 이 선을 못 넘는다(가장 확실한 장치).
2. **IP 당 상한** `IP_HOURLY`(30) · `IP_DAILY`(100): 넘으면 429. IP 는 소금(`SALT`)을 친 해시로만 저장.
3. **Cloudflare Turnstile**(사람 확인): Worker 에 `TURNSTILE_SECRET`, 페이지에 `VITE_TURNSTILE_SITEKEY` 를 넣으면 토큰 없는·틀린 요청은 403 — 브라우저가 아닌 스크립트의 대량 호출을 거른다.
4. **허용 출처만**: Origin 이 블로그·로컬 개발 주소가 아니면 403(다른 웹사이트가 방문자 브라우저로 부르는 것 차단).
5. **7일 캐시**: 같은 검색어는 네이버를 다시 부르지 않고 전체 상한도 쓰지 않는다.
6. **요청 검사**: `GET /search?q=` 만, 2~40자. 화면도 Enter·단추를 누를 때만 검색하고 같은 검색어를 되풀이하지 않는다.
7. 지도 JS·지오코더는 네이버가 Web 서비스 URL 로 인증한다(위 표). 차량 시간은 이 PC 에서만 재고 결과만 올리므로 공개 사이트에는 길찾기 호출이 없다.

로컬에서 가짜 네이버 서버로 확인한 것: 출처 없음·다른 출처 403, 짧은 검색어 400, 첫 검색 MISS → 같은 검색 HIT(네이버 호출 안 늘어남), 전체 상한 초과 503(네이버 호출 정확히 상한만큼), IP 시간당 초과 429, POST 404, Turnstile 실패용 키 403 / 통과용 키 200, 바다 좌표 결과 걸러짐.

### 공공데이터포털 API 키(상권·버스 — 이 PC 에서만)
`tools/location-compare/.env.local`(git 제외)의 `DATA_GO_KR_SERVICE_KEY` 에 넣었다(2026-10-13 상권 storeListInRadius 호출 확인). 값은 data.go.kr 마이페이지의 **일반 인증키(Decoding)**. 한 계정의 키는 승인된 API 모두에 같으므로 보통 `DATA_GO_KR_SERVICE_KEY` 하나만 채우고, 개별 칸은 비워 두면 공용 키를 쓴다. `VITE_` 를 붙이지 않는다(붙이면 공개 페이지에 들어간다). 이름에 숫자를 쓰지 않는다(스크립트의 `.env.local` 읽기가 `[A-Z_]+` 만 받는다).

| 변수 | API | 엔드포인트 |
|---|---|---|
| `SDSC_SERVICE_KEY`, `SDSC_DAILY_LIMIT` | 소상공인시장진흥공단 상가(상권)정보 | `https://apis.data.go.kr/B553077/api/open/sdsc2` (`storeListInRadius`·`storeListInUpjong`·`large/middle/smallUpjongList`) |
| `SEOUL_PATHINFO_SERVICE_KEY` | 서울특별시 대중교통환승경로 조회 | `http://ws.bus.go.kr/api/rest/pathinfo` |
| `SEOUL_BUS_ARRIVAL_SERVICE_KEY` | 서울특별시 버스도착정보조회 | `http://ws.bus.go.kr/api/rest/arrive` |
| `GG_BUS_ARRIVAL_SERVICE_KEY` | 경기도 버스도착정보 조회 | `https://apis.data.go.kr/6410000/busarrivalservice/v2` |
| `GG_BUS_STATION_SERVICE_KEY` | 경기도 정류소 조회 | `https://apis.data.go.kr/6410000/busstationservice/v2` |

### 상권 자료 — 통째로 받아 두고 이 PC 에서 찾기(한 달에 한 번)

후보지마다 API 를 부르지 않고, **경기·서울 상가 전체(약 123만 곳)를 SQLite 한 파일로 받아 두고** 거기서 찾는다. 후보지를 바꾸거나 반경·분류를 바꿔도 API 를 다시 부를 필요가 없다.

```bash
node scripts/stores-sync.mjs            # 매달 1번: 경기(41)·서울(11) 받기 → data/stores.sqlite (git 제외). 약 1,230회 호출·7분
                                        #   공단 기준월(stdrYm, 분기마다 바뀜)이 받아 둔 것과 같으면 아무것도 안 받고 끝남
node scripts/stores.mjs analyze         # 후보지별 분석 → src/commercial.json(페이지용) · COMMERCIAL.md(보고서)
node scripts/stores.mjs near 망포역 --r 500             # 반경 안 분류별 개수(후보지 이름·상호·"위도 경도" 아무거나)
node scripts/stores.mjs near 37.2486 127.0556 --cat cafe   # 그 분류 가까운 순 목록(--scls 코드 / --name 상호 도 됨)
node scripts/stores.mjs find 올리브영 --near 영통역 --r 2000  # 상호 검색
node scripts/stores.mjs codes 의원      # 업종 코드표
```

- 저장: `stores`(업소 1건 1줄: 상호·지점·대/중/소분류·행정동·주소·층·좌표) + `stores_rtree`(좌표 R-tree, 반경 검색) + `stores_fts`(상호·지점·건물명 트라이그램 전문검색) + `upjong`(업종 코드표) + `meta`(기준월·받은 시각). Node 26 내장 `node:sqlite` 라 설치할 것이 없다. 다른 도구(DB Browser for SQLite 등)로 열어도 된다.
- 안전하게 바꿔 끼우기: 새 자료는 `data/stores.next.sqlite` 에 받고 다 받은 뒤에만 `stores.sqlite` 로 바꾼다. 끊기거나 하루 호출 한도(resultCode 22)에 걸리면 받은 쪽을 기억해 두었다가 다시 실행할 때 이어 받는다(종료 코드 2).
- 분류(카페·음식점·화장품·마트·잡화점·필수의료·약국)는 `src/commercial-categories.json` — 소분류 코드·코드 앞자리·상호 이름(다이소·올리브영 등)으로 정한다. 고친 뒤 `analyze` 만 다시 돌리면 된다.
- 지수(점수)는 아직 정하지 않았다. `src/commercial.json` 에 개수·가장 가까운 거리만 있다.

### 보증금 1,000 기준 월세

보증금이 다른 매물을 한 기준으로 비교하려고 `월세 + (보증금 − 1,000) × 연 6% ÷ 12`(만원)로 맞춘다. 보증금 1,000만원 차이 = 월 5만원. 기준 보증금·전환율은 `src/data.ts` 의 `BASE_DEPOSIT`·`CONVERSION_RATE`.
